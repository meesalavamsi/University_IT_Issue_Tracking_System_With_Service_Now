# W-4: Audit History Review (investigation only; no platform changes)

> **Status:** investigated · **no change made** (per decision) · requires platform administrator review · 2026-11-11

## 1. Risk statement
Campus360 audits changes to personal fields (`audit=true` on `student`, `faculty` and others). ServiceNow stores those changes in **`sys_audit`** (raw old/new values) and presents them through **`sys_history_set` / `sys_history_line`**, which are generated per record when someone opens its history. If a privileged viewer generates a record's history, the lines contain sensitive old and new values. The question is whether a less-privileged user who can read the *record* (but not the *field*) can read those lines.

## 2. Affected platform tables (global, not owned by Campus360)
| Table | Contents | Current protection (verified read-only) |
|---|---|---|
| `sys_audit` | Every audited field change (old/new) | Deny-unless + allow `audit_viewer` / admin. Non-admin REST → **403** (W-2) |
| `sys_history_set` | One set per record and viewer generation | Allow/deny ACLs; non-admin REST → 403 |
| `sys_history_line` | Field-level lines of a set | Deny ACL plus allow ACL `6555da3d…` with script: **the line is readable only if the viewer can read the related record AND `relatedGR[field].canRead()`**. REST for leadership → **403** |
| Property `glide.history.role` | `itil` | Gates the History UI |

## 3. Evidence
| Observation | Result |
|---|---|
| Per-viewer history view (each persona generates their own set) | leadership, itil+HOD, instructor: **0** DOB lines; student (self) and registrar: 2 (approved) ✅ |
| REST to `sys_history_line` / `sys_audit` as leadership right after a registrar view | **403 / 403** ✅ |
| First impersonation run: leadership `GlideRecordSecure` query on lines generated by admin in the **same transaction** | 2 DOB lines readable ⚠️ |
| Second run, separate transaction | 0 ⚠️ conflicting |

The platform ACL script is **designed** to hide history lines for unreadable fields, and Campus360's field ACLs (now including D-2) are what that script evaluates. The one positive observation came from **server-side impersonation inside a single background-script transaction**, where access decisions may be cached across impersonated identities. It could not be reproduced over REST or in a separate transaction. **Root cause: unconfirmed.**

## 4. Possible mitigations (none applied)
| Option | Effect | Trade-off | Approval |
|---|---|---|---|
| A. Controlled retest with real logins (two browser sessions: registrar opens history, then leadership opens `sys_history_line_list.do?sysparm_query=set.id=<student>`) | Confirms or refutes the risk with no change | Manual | Test only |
| B. Keep `glide.history.role=itil` and don't give `itil` to Campus360 users who shouldn't see history | Limits who can open history UIs | Organisational | None |
| C. `no_audit` attribute on the most sensitive fields | Removes the data from history | **Conflicts with the audit requirement** | Not recommended |
| D. Customer ACL on `sys_history_line` | Platform-wide behaviour change | Global table, upgrade impact | **Separate approval** |
| E. Raise with ServiceNow Support if A reproduces | Vendor fix | Time | – |

## 5. Recommendation
Run option A after the next deployment, using the temporary-user procedure from W-2. If it reproduces, apply B immediately and request approval for D or E. Until then, treat W-4 as **open, low–medium**.
